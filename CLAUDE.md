### Этап 2 — Автозаполнение из исходников

> PM запрашивает у Разработчика файлы и разбирает их автоматически.

**Шаг 2.1 — Запросить файлы:**

```
PM спрашивает Разработчика:
"Пожалуйста, предоставь два файла в папку tools/:

 1. Файл основной конфигурации: <имя>.cf
    Конфигуратор → Конфигурация → Сохранить конфигурацию в файл...

 2. Файл расширения: <имя>.cfe
    — Если расширение уже существует:
      Конфигуратор → Расширения → выбрать → Сохранить в файл...

    — Если расширение новое — создай пустое:
      1. Конфигуратор → Конфигурация → Расширения конфигурации
      2. Создать → ввести имя расширения и префикс объектов
      3. Записать расширение (Ctrl+S)
      4. Правая кнопка на расширении → Сохранить в файл...
      5. Положить в tools/<имя>.cfe

 Сообщи мне точные имена файлов после того как положишь их в tools/."
```

**Шаг 2.2 — Разобрать и заполнить автоматически:**

```powershell
# Можно запускать параллельно:
tools\oscript\oscript.exe tasks\unpack.os --src tools\<имя>.cf  --dst tools\cf_src\
tools\oscript\oscript.exe tasks\unpack.os --src tools\<имя>.cfe --dst src\cfe\
```

Перед чтением XML дождаться завершения ОБОИХ процессов (exit code = 0, папки не пустые).

После разборки PM читает XML и заполняет параметры:

```
platform_version_min:
  1. Из tools/cf_src/Configuration.xml читать:
       - CompatibilityMode → версия_cf   (минимальная версия платформы для базовой конфигурации)
  2. Из src/cfe/Configuration.xml читать:
       - ConfigurationExtensionCompatibilityMode → версия_cfe  (совместимость расширения)
  3. Если версия_cfe = "DontUse":
       → спросить Разработчика: "Укажи минимальную версию платформы (напр. 8.3.14)"
     Иначе:
       → platform_version_min = max(версия_cf, версия_cfe)
         Значения вида Version8_3_14 сравнивать как числовые версии
```

```yaml
# Источник: max(CompatibilityMode из cf, CompatibilityMode из cfe)
# Источник: max(CF.CompatibilityMode, CFE.ConfigurationExtensionCompatibilityMode)
# CF: CompatibilityMode=8.3.14
# CFE: ConfigurationExtensionCompatibilityMode=8.3.14
# max(8.3.14, 8.3.14) = 8.3.14
platform_version_min: "8.3.14"

# Источник: src/cf/Configuration.xml → Name
base_config_name: "УправлениеНебольшойФирмойДляУкраины"

# Источник: src/cf/Configuration.xml → Version
base_config_version_min: "1.6.11.3"

# Источник: src/cf/Configuration.xml → Vendor
# Если Vendor пустой → конфигурация самописная → base_config_is_standard = false
base_config_vendor: "Molenari OU"

# Источник: src/cfe/Configuration.xml → Name
# Берётся из .cfe (существующего или нового пустого)
extension_name: "medtech"

# Источник: src/cfe/Configuration.xml → NamePrefix
# Берётся из .cfe (существующего или нового пустого)
# Задаётся разработчиком при создании расширения в Конфигураторе
extension_prefix: "мт_"
```

## Правила разработки расширений 1С

### Что МОЖНО в расширении
- Переопределять процедуры/функции через `&Перед`, `&После`, `&ВместоМетода`
- Добавлять новые реквизиты к объектам (с префиксом из `extension_prefix`)
- Добавлять новые объекты метаданных (с префиксом)
- Добавлять команды, формы, макеты к существующим объектам
- Подписываться на события через `ПодпискиНаСобытия`

### Что НЕЛЬЗЯ в расширении
- Изменять тип или структуру существующих реквизитов
- Удалять объекты исходной конфигурации
- Добавлять обязательные реквизиты без значений по умолчанию
- Дублировать функциональность из `KNOWLEDGE.md`

### Именование
```
Новые объекты:             <extension_prefix><Имя>
Переопределённые методы:   Расш_<ОригинальноеИмя>
```

## Стандарты BSL-кода

### Именование
- Процедуры/функции: `ГлаголСуществительное` (РассчитатьСумму)
- Переменные: `СуществительноеПрилагательное` (СуммаДокумента)
- Булевы: префикс «Это», «Есть», «Нужно» (ЭтоНовыйЭлемент)

### Запросы
- Только параметры — никакой конкатенации строк
- Поля перечислять явно, без `*`
- Запросы в циклах — **антипаттерн**
- Большие запросы — в макет типа «Текст»

### Транзакции
```bsl
НачатьТранзакцию();
Попытка
    // операции
    ЗафиксироватьТранзакцию();
Исключение
    ОтменитьТранзакцию();
    ВызватьИсключение;
КонецПопытки;
```

### Антипаттерны — никогда
- Данные через точку от результата запроса в цикле
- Глобальные переменные модуля для передачи данных
- Смешивание UI-логики и бизнес-логики

## Навыки (Skills) — парный программист

### Кто, когда и как использует навыки

Навыки используются **только Разработчиком** через Claude Code в VS Code.
PM и Заказчик с навыками не взаимодействуют.

Три момента применения:

```
1. Написание кода     → cc-1c-skills активируются по запросу разработчика
2. Ревью кода в IDE   → rules/ из claude-code-skills-1c применяются фоново
3. Ревью в CI/CD      → те же rules/ через Claude API в scripts/ai_review.py
```

#### Момент 1 — Написание кода (явный вызов)

Разработчик описывает задачу — Claude Code сам выбирает нужный навык:

| Что говорит разработчик | Навык | Действие |
|------------------------|-------|----------|
| «Создай внешнюю обработку для настройки лимитов» | `epf-init` | Создаёт структуру .epf |
| «Добавь форму к справочнику Контрагенты» | `form-add` | Добавляет управляемую форму |
| «Собери обработку в .epf файл» | `epf-build` | Компилирует из XML в .epf |
| «Зарегистрируй обработку в БСП» | `epf-bsp-init` | Подключает к подсистеме БСП |
| «Проверь форму на ошибки» | `form-validate` | Валидирует структуру формы |
| «Протестируй через веб-клиент» | `web-test` | Запускает тест в браузере |
| «Разбери макет отчёта» | `mxl-decompile` | Декомпилирует .mxl в JSON |

Слеш-команды для точного вызова: `/epf-init`, `/form-add`, `/mxl-compile` и др.

#### Момент 2 — Ревью кода в IDE (автоматически, фоново)

Правила из `~/.claude/rules/` (claude-code-skills-1c) применяются при каждом
обращении к Claude Code — разработчик не вызывает их явно.

Что проверяется автоматически:
- Именование объектов расширения (наличие префикса)
- Запросы в циклах (антипаттерн)
- Транзакции без обработки исключений
- Смешивание UI-логики и бизнес-логики
- Оптимальность запросов
- Корректность использования `&Перед`, `&После`, `&ВместоМетода`

#### Момент 3 — Ревью в CI/CD (автоматически, при каждом PR/MR)

`scripts/ai_review.py` вызывает Claude API с теми же правилами BSL.
Срабатывает автоматически при создании Pull Request / Merge Request.
Результат — комментарий к PR с замечаниями или «✓ Code review пройден».

## Стиль коммитов — Conventional Commits

Все коммиты в репозитории следуют формату [Conventional Commits](https://www.conventionalcommits.org):

```
<тип>(<область>): <описание>

Примеры:
  feat: add interactive src/ variant selector
  fix: unpack.os — functions before executable code (OneScript)
  refactor: move unpack.os to tasks/
  docs(CLAUDE.md): add conventional commits section
  chore: remove packagedef from ecosystem root
  ci: add production branch to triggers
```

### Типы

| Тип | Когда использовать |
|-----|-------------------|
| `feat` | Новая функциональность |
| `fix` | Исправление ошибки |
| `refactor` | Изменение кода без изменения поведения |
| `docs` | Только документация (md, комментарии) |
| `chore` | Служебное: зависимости, конфиги, gitignore |
| `ci` | Изменения CI/CD (workflows, gitlab-ci) |
| `test` | Добавление или исправление тестов |
| `style` | Форматирование, пробелы — без изменения логики |

### Правила PM

- PM формирует `CHANGELOG.md` из git log с группировкой по типам
- При проверке PR/MR PM проверяет соответствие заголовка коммита формату
- Коммиты с типом `feat` и `fix` попадают в CHANGELOG автоматически
- Коммиты `chore`, `ci`, `style` в CHANGELOG не включаются
